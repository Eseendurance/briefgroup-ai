# Brief Group AI Production Setup

## 1. Add Firebase Environment Variables

The app now includes Vercel-safe Firebase fallback values so deployment can work
even if your Vercel account does not show the variable form. Environment
variables are still supported and preferred for a cleaner production setup.

1. In VS Code, open the project folder: `C:\Users\HomePC\Desktop\briefgroup-ai`.
2. Copy `.env.example` and rename the copy to `.env.local`.
3. Go to Firebase Console, open your project, then open Project settings.
4. In Your apps, copy the web app Firebase config values.
5. Paste the values into `.env.local`.
6. In Vercel, open the project, not the Team settings page.
7. Go to Settings, then Environment Variables.
8. Click Add New if the button is visible.
9. Add the same variables from `.env.local`.
10. Redeploy the Vercel project.

Do not commit `.env.local`. The `.gitignore` already protects `.env*`.

If the Add New button is not visible in Vercel, continue deployment anyway. This
codebase will use the fallback Firebase web config from `app/lib/firebase.ts`.

## 2. Secure Firebase Auth

1. In Firebase Console, open Authentication.
2. Enable Email/Password sign-in.
3. Add your real admin email to `NEXT_PUBLIC_ADMIN_EMAILS`.
4. In Vercel, update `NEXT_PUBLIC_ADMIN_EMAILS` with the same email.
5. Visit `/register`, create your account, then visit `/dashboard`.
6. Visit `/admin` only with an email listed in `NEXT_PUBLIC_ADMIN_EMAILS`.

## 3. Publish Firestore And Storage Rules

1. Open Firebase Console.
2. Go to Firestore Database, then Rules.
3. Copy the contents of `firestore.rules`.
4. Replace `replace-with-your-admin-email@example.com` with your admin email.
5. Publish the rules.
6. Go to Storage, then Rules.
7. Copy the contents of `storage.rules`.
8. Publish the rules.

## 4. AI, Rate Limits, and Persisted Pilot Data

Set these server-side environment variables in `.env.local` and in Vercel:

- `GEMINI_API_KEY`: a Google AI Studio key for the server-side BriefGroup AI
  preview. Never prefix this key with `NEXT_PUBLIC_`.
- `GEMINI_MODEL`: defaults to `gemini-2.5-flash`.
- `UPSTASH_REDIS_REST_URL` and `UPSTASH_REDIS_REST_TOKEN`: production
  sliding-window rate limits. Production API routes return `503` when Redis is
  not configured instead of quietly falling back to instance-local limits.

`/api/ai/chat` is the public, rate-limited preview. Its farming, equipment,
inspection, operations, and general guidance is generated by the configured
AI provider. Do not enter confidential or personal information in the public
preview.

The dashboard uses Firebase Authentication, Firestore, and Firebase Storage:

- Account onboarding saves a user profile and optional wellbeing preference in
  `users/{uid}`.
- User-created operational summaries are saved in `reports`.
- Uploaded inspection files are stored under `inspections/{uid}/` and their
  metadata is saved in `inspections`.
- Signed-in customer-care conversations are saved in `aiInteractions`.

Publish both `firestore.rules` and `storage.rules` in Firebase Console before
using these features. The dashboard currently has no connected site sensors;
weather is real Open-Meteo data for the coordinates entered by the user, and
the operational summary is a transparent calculation from user-provided
values, not an AI diagnosis.

The existing weather and report API routes verify Firebase ID tokens and use
rate limits. The public AI preview does not require an account.

## 5. Workspaces, database, and billing

Firebase remains the authentication and operational-data layer. PostgreSQL with
Prisma stores workspace membership, trials, billing provider references, audit
events, and white-label settings. A Firebase UID is used as the external user
identity; no Firebase passwords are copied to PostgreSQL.

1. Provision PostgreSQL with pooled and direct connection URLs.
2. Set `DATABASE_URL` to the pooled application connection and `DIRECT_URL` to
   the direct migration connection.
3. Run `npm run db:deploy` after creating and reviewing a migration. For local
   schema development, use `npm run db:migrate -- --name workspace_billing`.
4. Run `npm run db:generate` after schema changes.
5. Configure `APP_BASE_URL` with the canonical HTTPS origin.
6. Configure at least one payment provider using the variables in `.env.example`.
   Stripe prices must be monthly USD prices of exactly $29 and $99. The checkout
   endpoint checks price currency, interval, and amount before creating a session.
   Paystack plan codes and amounts are configured in NGN minor units (kobo);
   Flutterwave uses merchant plan IDs and NGN amounts.
7. Register each webhook with the provider:
   - Stripe: `/api/webhooks/stripe`
   - Paystack: `/api/webhooks/paystack`
   - Flutterwave: `/api/webhooks/flutterwave`
8. Use test credentials and provider test-mode webhook deliveries before enabling
   production keys. Never put secret keys in `NEXT_PUBLIC_` variables.

New registrations create a 14-day trial workspace and an OWNER membership.
`/workspace` displays current plan state, member roster, and editable workspace
branding. Billing state changes only after a verified webhook; returning from
checkout alone does not grant paid access. The report-generation write route and
workspace settings route enforce trial/subscription access server-side.

Paystack and Flutterwave amounts are required configuration; checkout fails
closed when merchant plans or amounts are missing. Confirm their plan amounts,
renewal cadence, taxes, and supported currencies in the merchant accounts before
using real payment credentials. Customer invitations and automated email delivery
are not enabled yet. Custom-domain values are stored but DNS and routing still
require separate setup.

The public pricing is a USD reference for Stripe. The regional gateways display
their configured NGN amount at provider checkout. The website's pilot scenarios
are illustrative measurement plans, not customer testimonials or proven savings.
No SOC 2 / ISO 27001 certification, dedicated database, SLA, or enterprise
integration is claimed without independent evidence and a signed agreement.
Seat limits and AI-credit budgets are not yet metered or enforced automatically.
The billing guard is applied to report generation and workspace settings APIs;
existing direct Firebase Storage / Firestore mutations do not consult PostgreSQL
subscription state and must not be treated as a complete platform-wide paywall.

## 6. Add A Custom Domain From Truehost To Vercel

1. In Vercel, open your Brief Group project.
2. Go to Settings, then Domains.
3. Add your domain, for example `briefgroup.com`.
4. Vercel will show DNS records to add.
5. Log in to your Truehost cPanel.
6. Open Zone Editor under Domains.
7. Click Manage next to your domain.
8. Add or edit the apex/root record:
   - Type: `A`
   - Name: `@`
   - Value: `76.76.21.21`
9. Add or edit the `www` record:
   - Type: `CNAME`
   - Name: `www`
   - Value: the CNAME target Vercel shows for your project
10. Save the records.
11. Return to Vercel and click Verify.
12. Wait for DNS propagation. It can take a few minutes, and sometimes longer.

If Truehost already has old website records for `@` or `www`, edit those
records instead of creating duplicates.

## 7. Deploy From VS Code

Run these commands in the VS Code terminal:

```bash
npm run build
git status
git add .
git commit -m "Add production security and SaaS features"
git push origin main
```

After the push, Vercel will redeploy automatically from GitHub.
